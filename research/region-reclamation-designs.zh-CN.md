# 如何处理区域内部的独立对象寿命

[English](region-reclamation-designs.md) | 简体中文

调研日期：2026-11-11。本文接续 [Goose 设计研究](beyond-goose.zh-CN.md)，依据已有机制的一手资料讨论具体方案。组合设计尚未实现或证明，本轮没有新增性能实验。

## 分清三个问题

扩展 Goose 时，需要区分 **对象什么时候应该消失**、**什么时候已没有操作访问其存储**、**如何复用或归还存储**。池和分配器主要回答第三问；代数检查在查找时验证身份；安全访问区间回答第二问的一部分。它们单独都不能发现任意图节点已经不可达。

严格不使用追踪式 GC／逐对象 RC 的方向中，我认为最值得验证的是：Goose 作用域数据栈，加上 **可回收的长期对象容器、生命周期关系和短访问阶段**。目标是自动处理存储与访问安全，把寿命选择集中到数据模型声明及少量业务操作，而不是完全消除这些选择。

## 可回收容器：区域也支持独立删除

普通作用域数据继续使用 Goose 式数据栈。需要独立删除的实体放入另一类容器，底层采用可复用块、槽位，以及处理变长载荷的大小分类或连续区间分配。删除时复用槽位；元数据和未完成访问允许时归还空块。分配可能需要申请新块，碎片仍然存在。这给语言增加了分配器选项，但不必每创建一个对象就调用一次通用分配器。

Reaps 已提供分配器层面的先例：同时支持整个区域回收和单个对象删除。它本身不提供语言级内存安全，不推断删除时机，也不保证存储始终紧凑。2002 年论文的性能结果不能当作与今天 Goose 的对比。[Reaps 论文](https://people.cs.umass.edu/~emery/pubs/berger-oopsla2002.pdf)

容器外部的链接使用可验证句柄，物理视图只短期存在。没有视图或外部保留指针阻碍时，可以通过稳定槽位表搬移载荷，但需要间接访问和搬移成本。身份元数据必须支持安全查找，包括容器销毁和地址复用以后。代数耗尽时应停止复用该身份，不能假定回绕永远不发生。

## 生命周期关系：粗粒度、声明式地决定删除

区分两种关系：拥有关系控制子对象寿命；观察关系只标识对象，不延长其寿命。例如文档拥有语法节点，导航链接和编辑器选区通过句柄观察节点。删除子树时安排删除其拥有的后代，观察者随后得到对象不存在的结果。

简单核心可以要求拥有关系形成森林：每个可变实体只有一个父拥有者，不允许拥有关系成环；观察链接可以任意成环。包含关系可以提供常见默认值，但重新挂接和真正的共享寿命需求仍要明确策略，语言需要在更新时检查或维护拥有关系的不变量。这是把指针记账变成数据模型选择，不能推断业务认为什么已经过时。

Flecs 有具体的关系清理策略，包括删除父实体时删除子实体。这是声明式清理的先例，不代表 Flecs 是内存安全语言。Vale 也展示了非拥有引用与单一所有权的组合，其指南仍要求每个可变结构只有一个拥有引用。两者都没有消除所有权语义。[Flecs 清理策略](https://www.flecs.dev/flecs/ComponentTraits.html) · [Vale 引用模型](https://vale.dev/guide/references)

级联清理的成本取决于实际工作：子对象、索引、关系和外部资源都可能需要处理。存储区域重置不会把这些语义上的清理变成常数时间。

## 访问阶段：保持视图有效，结构修改延后提交

建议初版让每个长期容器由一个任务控制。进入短访问阶段后，句柄经检查可以产生物理视图；编译器把视图绑定到该阶段，拒绝逃逸和携带存活视图挂起，并阻止回调绕过该阶段的结构修改限制。阶段内，不改变布局的数据可以保留多个别名。任务并发执行时，写入还需要另外的规则。

会搬移已有数据的插入、删除、改变存储类型和压缩操作，在访问期间被禁止或排队。最简单的删除契约是：**删除在最外层访问阶段提交时生效，发出请求时不立即生效。** 既有视图保持有效，该阶段内的新查找也遵循提交前的结构状态。所有视图结束后，提交删除、使句柄失效、执行规定的清理，再允许复用存储。重复命令、回调重入、错误和取消都需要明确语义。

仅为示意语法，不是 Goose 代码：

```text
phase(store) {
    if let node = store.get(id) {
        update_fields(node)
        store.defer_delete(id)
        inspect(node)              // 本阶段结束前仍然有效
    }
}                                  // 提交删除；旧 id 此后查找失败
```

Flecs staging 已通过结构操作排队保持迭代有效，并明确说明延迟操作会改变更新何时可见。语言可以跨函数检查相应的访问限制，减少对库使用纪律的依赖。这是小型语言协议的设想，不是整个设计已经正确的证明。[Flecs staging](https://www.flecs.dev/flecs/Systems.html#staging)

这样可以避免每复制句柄就更新计数，并在验证后使用物理引用执行阶段内循环。代价是阶段边界、命令缓冲、延迟可见性和清理延迟。漫长或停滞的阶段会阻止回收；待处理命令量需要背压或失败策略，不能在视图仍存活时偷偷提交。如果必须立即让删除对新查找可见，可以另设接口：先使新查找失败，保留旧载荷直到读取者结束，但其快照和修改语义必须另外规定。

## 并发读取：回收协议不等于完整并发模型

后续扩展可以使用 RCU 或 epoch 回收，把移除和物理销毁分开，在相关读取者结束后才释放待回收存储。它们不发现任意不可达对象，也不会自动使冲突读写安全。发布的数据版本仍需要不可变更新、原子操作、锁或其他同步规则。[Linux RCU 概念](https://www.kernel.org/doc/html/latest/RCU/rcu.html) · [RCU 不保证的性质](https://www.kernel.org/doc/html/latest/RCU/Design/Requirements/Requirements.html)

Crossbeam 文档说明，处于 pinned 状态的参与者会延迟新移除对象的回收。因此不能让访问阶段无限期跨越异步挂起而不付代价。应使用有界访问区间，或把缓冲区交给独立的操作拥有者，直到真正完成后才回收；发出取消请求不是完成。RCU／epoch 不属于追踪式收集，但确实是运行时回收机制，有些库也称其为 GC。[Crossbeam epoch 管理](https://docs.rs/crossbeam/latest/crossbeam/epoch/index.html)

无 RC 核心应先采用可变容器单一管理者，加上结构化不可变共享或整容器转移。句柄身份不能授予转移后的访问权，查找还需要当前权限。共享可变容器应当作为独立扩展，另行处理同步与回收的证明责任。

## 改善作用域数据和小视图滞留

编译器证明拥有者及其全部别名都不再使用时，可以通过最后使用分析缩短拥有者寿命，改善 Goose 同一代码块内的数据栈复用。该优化应限于提前释放存储不会改变可观察资源清理或外部访问的值。无法证明时，可以建议缩小作用域；它不会回收仍存活容器内部已经无用的各个元素。

对于长期保留的小切片，提供独立值操作，把选中数据复制到适当目标。不可变值接口可以允许显式选择“将小切片与大缓冲区分离”的策略。必须保持视图身份、可变性和别名语义，不能悄悄把可变视图变成独立副本。分块输入可以减少保留的底层存储，但增加跨块处理，也不再保证始终连续。

## 任意图的完全自动回收需要另一种策略

如果要求任意强引用环，并在最后一条外部路径消失后自动回收，用户既不声明生命周期拥有者，也不执行业务删除，上述核心就不够。区域内追踪收集是直接的可选方案：从登记的根出发，回收选定容器中的不可达节点。跨区域传入的强引用必须登记为根，或以其他方式参与生命周期协议。隔离可以限制暂停影响范围，却不会让扫描、写屏障、元数据和资源清理免费。

这个选项就是 GC，不满足严格非 GC 的要求。引用计数加引用环处理是另一种有成本的选择。它们都不应被悄悄放进声称具有核心回收保证的接口。混合设计可以把容器策略显式区分，让作用域数据继续走低成本路径。

后续研究 [Goose 式数据栈与 GC 回退路径](goose-hybrid-gc.zh-CN.md) 放宽严格非 GC 的约束，进一步讨论自动选择存储和跨内存引用的安全条件。

## 建议的原型边界

从 Goose 式作用域数据栈，加单一管理者的可删除容器开始。实现可验证身份、小型拥有／观察关系声明，以及延迟结构修改的同步访问阶段。编译器推断聚焦引用有效性、阶段逃逸和安全存储复用。递归载荷和变长数据交给容器分配器，不要求每个实体拥有静态编号的数据栈。

随后检验困难情况：视图存活时经回调请求删除、把父节点挂到后代下面、提交失败、仍有外部观察句柄时删除、带复制句柄转移容器、容器销毁后句柄仍存在、代数耗尽，以及未完成 I/O 的取消。测量长阶段下的滞留和尾延迟、元数据与间接访问、碎片，以及新增注解和代码重构。先证明这个小协议，再扩展到并发修改或任意图的自动收集。

这个组合可以解决独立删除与安全复用，并减少手动记账。核心边界是明确的：业务关系或操作决定寿命，编译器和运行时安排安全访问与回收。
