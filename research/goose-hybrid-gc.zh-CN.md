# Goose 式数据栈与 GC 回退路径

[English](goose-hybrid-gc.md) | 简体中文

调研日期：2026-11-14。本文是架构评估，不是已经实现的 Goose 扩展或新基准。Goose 的基线描述对应此前检查的 `32a4f445d8a94b22874a28469f95f69ba3ac31dd`；[数据栈实验](../experiments/goose-stacks-2026-11-11/README.md)使用的是 11 月 11 日的 `f4637bf` 编译器。本文不声称审计了此后的全部上游变化。

**如果优先目标是自动内存安全、减少源码管理负担，而不是绝对禁止 GC，这是一条值得重视的路线。** 能静态证明合适的数据使用数据栈，保留低成本分配、紧凑布局和整体回收；动态共享、独立寿命较复杂的对象交给追踪收集，减少手动拥有关系与删除协议。总体性能更好是需要测量的假设，不是把两种机制放在一起就自然成立。

## 这个原则已经有扎实先例

MLKit 已结合区域推断与 GC。Elsman 和 Hallenberg 的 2021 年工作将分代收集、带类型区域和紧凑表示结合起来。其方案通过扫描指定的可变区域避免分代写屏障，是以收集阶段工作换取更少的更新记账，不能理解为修改完全免费。MLKit 的表示和类型系统与 Goose 不同。[2021 年论文](https://elsman.com/mlkit/pdf/jfp2021.pdf)

后续 PLDI 2023 论文发现并修复了早期区域／GC 类型理论中涉及高阶多态程序的健全性问题：应用代码不会再解引用的区域指针，仍可能被收集器通过存活闭包或对象扫描。因此，收集器安全需要比“应用访问安全”更强的条件。新设计应参考修正后的论证，不能把早期所有证明都当作充分依据。[2023 年安全性论文](https://elsman.com/mlkit/pdf/gcsafe-pldi23.pdf)

Go 的标准实现是熟悉的例子：自动选择栈分配，不能证明局部值寿命局限于栈时使用 GC 堆。Goose 的潜在价值在于更丰富的多数据栈安排、目标位置构造和紧凑变长布局，有机会让更多动态数据离开追踪堆。究竟多多少、编译代价多大，尚未测量。[Go 分配说明](https://go.dev/doc/faq#stack_or_heap) · [Goose 存储模型](https://github.com/aardappel/goose/blob/32a4f445d8a94b22874a28469f95f69ba3ac31dd/docs/reference.md#4-where-values-live)

## 首先把自动选择做成编译器决策

建议规则是：值或一类分配点的寿命、增长、引用关系和表示满足数据栈不变量时，使用数据栈；否则从构造开始就使用 GC 存储，接受保守推断带来的性能成本。发生逃逸不一定必须用 GC：新返回值直接构造到调用者目标，就可能已经解决寿命问题。反过来，证明寿命有界，也不代表一定存在合适的数据栈表示。

不要把回退简单实现为“运行时发现逃逸后再搬过去”。搬移已有别名的可变对象，需要保持身份、更新别名，并处理内部指针和相对引用；可能必须连同依赖图一起搬移。只有独立值语义允许时，显式复制才合适。首版应在执行前分类可能逃逸的分配点，运行时提升作为之后单独规定的优化。

不同分配选择应保持源码语义稳定：对象身份、别名、修改和资源清理不能依赖优化是否成功。依赖存储的接口、原始地址、FFI 和持久化布局需要明确契约。函数可能需要存储多态实现，或在接口处使用统一表示；增加 GC 分支不会自动使 Goose 的所有现有表示相互兼容。

## 两类内存之间的引用规则最关键

- **数据栈指向 GC 对象**：必须通过生成的根映射、登记槽位或精确区域描述符，纳入收集器的存活根。不含 GC 引用的纯字节缓冲区可以不扫描；数据栈上保存 GC 引用的容器，并不会自动免于收集工作。
- **长期 GC 对象指向短期数据栈**：除非证明目标寿命足够，否则禁止此边，或为整个逃逸依赖安排兼容存储。GC 看到地址，不会自动阻止独立回退的数据栈被回收。可以延长整块区域寿命，但可能保留远超引用目标大小的数据。
- **GC 对象指向 GC 对象**：遵循普通追踪规则，分代或并发收集可能需要写屏障或其他可靠的边记录策略。引用环在不再被任何根到达时可以回收。
- **数据栈指向数据栈**：继续使用 Goose 式引用根和作用域检查。增加 GC 不应削弱缩减、改变存储类型和内部引用有效性的规则。

每个收集点还必须能正确描述构造到一半的对象、临时值和已弃用槽位。应用活跃性与收集器看到的可达性，需要对哪些指针字段仍然有效达成一致。Goose 的紧凑变长值、相对链接和内部指针都需要编译器配合；不能把任意机器字都当成普通对齐地址来扫描。

## 明确 GC 的回收单位

GC 可以把整份紧凑文档或区域作为一个单元，让其寿命脱离词法作用域，同时保留内联布局。这有用，但只要一个视图保留整个单元，就不能独立回收其中的无用节点，因此只解决长期容器问题的一部分。

需要独立死亡的实体，应使用可独立追踪的对象，或具有合适子对象元数据的块。载荷仍然可以内联字符串和小数组。收集器必须知道合法内部引用属于哪个拥有对象。回收任意中间空洞需要额外布局机制，在巨型 arena 前面加一个 GC 头并不能做到。

移动式收集会使稳定引用、FFI 和跨回收单元的相对偏移更复杂。首个原型采用精确、非移动的标记清扫是合理选择，可减少搬移处理，但会引入元数据、清扫成本和碎片。它也不会解决已有连续对象的增长：稳定可增长数组仍需要相应的地址预留、分块、间接层或更新协议。非移动 GC 只是收集器不搬对象，不代表容器扩容永远不搬数据。

## 让成本边界可见

减少追踪堆分配可能降低收集频率和工作量，但结果取决于分配速率、存活对象、根、指针密度、滞留和具体收集策略。少量 GC 分配仍可能形成很大的长期对象图，或导致昂贵的根扫描。不能推导“只有 10% 的分配进入 GC，就只剩 10% 的 GC 成本”。[Go GC 成本指南](https://go.dev/doc/gc-guide)

不含 GC 引用的纯数据栈路径，可以避免很多收集器记账；混合路径仍可能需要根、安全点和收集器特定屏障。并发与分代收集在暂停、同步、内存余量和实现复杂度之间取舍。此前 Goose 整数循环的成绩不能预测这些成本。

建议默认自动选择，同时输出分配报告，说明哪些值进入 GC 堆、原因是什么。对选定函数或模块，提供沿调用链检查的 **不分配 GC 对象契约**；违反时编译失败，不悄悄更换策略。该契约不保证没有 GC 暂停，因为函数可能持有根，或同进程其他任务触发收集。更强的隔离或延迟保证需要单独设计运行时。

文件、锁、设备与取消的确定性清理也应与内存收集分开。GC 防止可达存储被回收，却不自动保证尾延迟、按时关闭资源或无数据竞争；缓存仍然可达的数据，也不会因为业务觉得没用而被自动收集。

## 可行的实现顺序

首先实现单工作线程收集器，保留现有线程隔离。加入精确根登记和追踪元数据、保守的编译期分配分类，以及支持少数对象布局的非移动收集器。先禁止不安全的跨内存引用，暂不尝试任意运行时提升。检验混合引用链和环、存活闭包里的源码死引用、内部指针、缩减、部分初始化和 FFI 保留引用。

然后扩展布局与存储多态接口，用缓存的跨过程摘要优化分类。GC 回退可以让有界分析在不静态解决所有寿命关系的情况下安全接受程序，但不能消除表示与接口约束。需要测量编译时间和诊断质量，才能讨论 Go／Zig 级开发编译体验。

按工作线程分离堆，有望在保留隔离的同时限制收集影响范围。跨线程图转移或不可变共享仍需要明确的拥有／根协议，本地收集器不会让任意跨线程引用自动安全。Verona 的隔离区域研究也探索了内存策略的局部化，同时具有自己的能力约束。[Verona 研究](https://arxiv.org/abs/2309.02983)

验证负载应包括主要使用作用域存储的解析流水线、持续增删的长期循环图，以及从临时计算中保留视图或闭包的混合场景。对照包含可表达该任务的纯 Goose、开关分配优化后的混合版本、Go，以及设计合理的 C／Rust 存储。记录各域分配、根扫描量、存活和滞留字节、RSS、吞吐、收集与尾延迟、屏障、全量／增量编译和源码管理工作。只有新增机制被实际负载中的收益抵消，混合设计才真正占优。

对于本项目关注的目标，这值得作为优先研究方向，与要求所有长期图都遵循显式区域／删除协议的路线并行评估。目标是普通代码自动管理寿命，能证明合适的路径使用便宜的数据栈，关键代码具有明确性能契约；不能承诺任意代码都获得 Goose 当前数据栈的成本。
